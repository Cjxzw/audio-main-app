# Skill 与 Harness 结构化动作改造方案

## 1. 背景

当前 App 将一部分能力封装在系统 Skill 中。LLM 先调用原生 `skill_use` 加载 Skill，随后根据 Skill 文档输出正文 JSON，由 Harness 将其转换成内部调用并执行。

实机日志显示，“本地执行”Skill 加载后，LLM 会频繁把下一步动作塞进 `skill_use.resource_name`，例如把 `read` 的 JSON 当成附件名。由此产生以下问题：

- `skill_use` 被反复调用，Skill 正文被重复注入。
- `resource_name` 收到动作 JSON 后返回“Skill 文件不存在”。
- 重复调用保护最终阻止继续执行。
- LLM 将协议错误归因成文件读取失败，并向用户输出无效的道歉回复。

初步判断是两套协议在表达上过于相似：`skill_use` 使用原生工具调用，而 Skill 文档又要求 LLM 输出类似原生工具调用的 `name`/`arguments` JSON。模型容易把后者理解成前者的嵌套参数。

本方案分两个阶段推进。第一阶段只调整 Skill 文档提示词并进行实机验证；只有第一阶段无法将错误率降至可接受范围时，才进入 Harness 协议改造。

## 2. 目标与约束

### 2.1 目标

- 保持常驻原生工具列表稳定，避免因动态增删工具定义造成提示前缀和 KV 缓存大幅变化。
- 降低 Skill 加载后重复调用 `skill_use`、误用 `resource_name` 的概率。
- 将按需开放的能力描述成 Harness“结构化动作”，不再引导 LLM 将其理解为另一套工具调用。
- 若进入第二阶段，使 Harness 同时支持新结构化动作、现有原生 `tool_calls` 和旧版正文调用格式。

### 2.2 约束

- 第一阶段不得修改 Harness、AgentLoop、工具注册表和持久化逻辑。
- `skill_use` 必须保持通用，不加入仅针对某个系统 Skill 的特殊指令。
- Skill 内部稳定 ID 暂时保留 `local-execution`，避免破坏升级覆盖、禁用状态、版本记录和历史数据。
- “隐藏工具包”仅作为展示名称；Skill 正文中将其能力称为“结构化动作”或“动作包”。
- 第二阶段开始前必须基于第一阶段实机日志再次确认。

## 3. 第一阶段：仅优化 Skill 文档

### 3.1 改名

将系统 Skill 的展示名称从“本地执行”改为“隐藏工具包”，内部 ID 仍为 `local-execution`。

建议元数据：

```yaml
name: 隐藏工具包
description: 按需开放本地文件、命令、HTTP、代码图谱等 Harness 结构化动作。
```

### 3.2 提示词原则

SKILL.md 不再使用以下说法：

- 隐藏工具调用
- 原生工具或模拟工具
- function calling
- `name`/`arguments` 工具 JSON
- “把工具调用作为唯一正文输出”

改为说明：Harness 能识别特定的结构化动作。需要执行时，LLM 按动作格式输出并传入参数；Harness 返回结果后，LLM 再决定输出下一个动作或最终回答。

第一阶段尚未修改解析器，因此实际输出格式必须继续使用当前 Harness 已能解析的兼容格式。文档措辞先去工具化，但不能在这一阶段擅自换成解析器尚不支持的新标签。

建议在文档开头明确状态转换：

1. 当前 Skill 内容已经加载完成。
2. 不要为了执行动作再次调用 `skill_use`。
3. `resource_name` 只用于读取该 Skill 自身列出的附件，不能承载动作或任务参数。
4. 需要执行时，直接按本 Skill 规定的结构输出动作。
5. 收到 Harness 结果后，继续输出下一动作或普通最终回答。

### 3.3 第一阶段改动范围

只允许修改：

- `app/src/main/assets/skills/local-execution/SKILL.md`
- 如系统 Skill 安装/升级依赖版本摘要，可由构建过程自然更新对应版本，不手工修改运行逻辑。

不修改：

- `SkillRegistry`
- `MainToolRegistry`
- `AgentLoop`
- `StructuredOutputParser`
- `VoiceAgentService`
- 对话存储和 checkpoint

### 3.4 实机验证用例

至少连续执行以下场景，每类不少于 5 次：

1. 加载 Skill 后读取 `/logs/voice-agent.log` 尾部。
2. 加载 Skill 后读取 `/source` 中指定源码文件。
3. 加载 Skill 后执行一条只读命令。
4. 在同一回合中连续执行两个不同动作。
5. Skill 已加载后，用户要求“继续”。

重点统计：

- `skill_use` 首次成功后被无附件地重复调用的次数。
- `resource_name` 收到 JSON、虚拟绝对路径或动作内容的次数。
- “Skill 文件不存在”的次数。
- 重复动作被策略阻止的次数。
- 完成任务所需模型轮次。
- 最终回答是否错误声称无法使用动作。

### 3.5 第一阶段通过标准

建议满足以下条件后保留轻量方案：

- 25 次基础用例中没有动作 JSON 被塞入 `resource_name`。
- 无连续重复 `skill_use`。
- 单动作任务成功率不低于 96%。
- 连续两动作任务成功率不低于 90%。
- 未出现因格式错误而生成的用户可见失败回复。

若仍出现稳定复现，或成功率明显依赖具体措辞，则进入第二阶段。

## 4. `skill_use` 通用行为约定

该部分是后续可能实施的独立优化，不纳入第一阶段文案实验。

单文档 Skill 首次加载成功后，应只表达通用事实：

```text
Skill：隐藏工具包
状态：已完全加载
版本：<version>
内容：
<skill_content>
...
</skill_content>
```

不额外追加针对“隐藏工具包”的动作指导；所有领域行为由 SKILL.md 自己声明。

多文档 Skill 加载核心文档后仍返回附件清单。`resource_name` 仅用于按需加载清单中的 Skill 内部 UTF-8 文本附件。

已经完全加载的单文档 Skill 再次无附件调用时，可只返回“此前已完全加载”，避免重复注入完整正文。是否实施该行为需要确认它不会破坏 CONVERSATION 类型 Skill 的恢复逻辑。

## 5. 第二阶段：Harness 结构化动作协议

仅在第一阶段验证失败后实施。

### 5.1 新协议

建议采用与原生 function calling 明显不同的格式：

```text
<HARNESS_ACTION>
{"action":"read","input":{"path":"/logs/voice-agent.log","tail_lines":100}}
</HARNESS_ACTION>
```

约束：

- 一次只允许一个动作。
- 动作块必须是本轮助手输出的唯一有效正文。
- 外层字段固定为 `action` 和 `input`。
- 不使用 `tool`、`function`、`name`、`arguments` 或 `tool_calls`。
- 代码围栏和 `<DETAILS>` 内的示例永不执行。
- 普通最终回答不得包含动作标签。

### 5.2 Harness 解析优先级

1. API 原生 `tool_calls`。
2. 新 `<HARNESS_ACTION>` 结构化动作。
3. 旧版正文工具 JSON兼容格式。
4. 普通最终正文。

旧格式只保留解析兼容，不再出现在系统提示词或 Skill 文档中。待实机日志确认没有旧格式后再决定是否移除。

### 5.3 执行链路复用

新动作解析后转换为现有内部调用对象，继续复用：

- Skill 激活状态和授权校验
- 参数 schema 与路径策略
- 重复调用保护
- 执行器及超时控制
- UI 工具状态、诊断日志和 trace
- checkpoint、取消和恢复流程

不得为结构化动作另建一套绕过安全检查的执行器。

### 5.4 必要防护

- 只有当前回合已激活对应系统 Skill，才允许执行其动作。
- TURN 类型 Skill 在用户回合结束后撤销授权。
- `skill_use.resource_name` 拒绝 JSON、动作标签、绝对虚拟路径和路径穿越内容。
- 格式错误时返回针对性修复信息，不得笼统返回“Skill 文件不存在”。
- 已加载 Skill 再次无附件调用时，不重复注入全文。
- 日志区分 `native_tool`、`harness_action` 和 `legacy_body_call`。
- 连续重复动作沿用现有拦截策略。

### 5.5 第二阶段测试

- Skill 加载后正确执行单个和连续多个动作。
- 动作被错误塞入 `resource_name` 时得到定向纠正。
- 未加载 Skill 时动作被拒绝。
- TURN 权限在回合结束后撤销。
- 动作示例位于代码围栏或 `<DETAILS>` 时不执行。
- 原生工具调用保持正常。
- 旧版正文格式仍能执行。
- 非法 JSON、未知动作、缺失参数和超长正文均被安全拒绝。
- checkpoint 恢复后不会越权继承 TURN 动作。

## 6. 与语音摘要问题的关系

语音摘要重复是独立问题，不应与 Skill 实验混在同一次验证中。

已确认的原因是：原始回复已有“正文 + `<DETAILS>`”且正文超过阈值时，摘要流程会删除原标签，再把原正文和原详情整体包入新的 `<DETAILS>`，造成正文重复。

后续修复原则：已有有效 `<DETAILS>` 且正文非空时，直接使用原正文作为播报文本并保留原始展示内容，不再发起额外摘要请求。该修复应单独提交和测试。

## 7. 实施顺序

1. 只修改“本地执行”SKILL.md 的名称、描述和行为措辞。
2. 构建并安装测试包。
3. 按第一阶段用例采集实机日志和成功率。
4. 第一阶段达标则停止，不修改 Harness。
5. 第一阶段不达标，再评审并实施 `skill_use` 通用行为优化。
6. 仍不足时实施 `<HARNESS_ACTION>`、兼容解析和安全校验。
7. 语音摘要重复问题使用独立改动处理。
